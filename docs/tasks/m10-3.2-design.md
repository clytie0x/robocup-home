# M10 design: section 3.2 on the existing runtime

This file chooses the next task and the smallest boundary that can show a second task reusing `sim_runtime`. It authorizes no crate, workflow, or dependency change. The acceptance inventory is [3.2 General Purpose Service Robot](3.2-general-purpose-service-robot.md). The implementation order is [M10 section 3.2 plan](m10-3.2-plan.md).

## Choice

The next task is section 3.2 General Purpose Service Robot.

The book contents and the Stage I contents on printed page 13 list it immediately after 3.1 Carry My Luggage. The section starts on printed page 18 and continues on printed pages 19 and 20. Those are physical pages 23, 24, and 25 in the attached PDF. Cover 2024 Rev-1, revision 2024-07-09. Hash `da69e2c276836ccb228ab3a9ba403b04efe38d7a1d30a7d4cbdcc490d83ce600`.

The printed cycle that a small machine can represent is:

1. The robot starts outside the Arena.
2. When the arena door is open, the robot moves to the Instruction Point.
3. The operator then instructs a command. The command body is not in the PDF.
4. After the first command, and after the second, the robot returns to the Instruction Point. Procedure step 4 also says the robot goes back and waits for the next command. Whether the third command requires that return stays open.
5. The maximum time is 5 minutes. The referee might pause the timer at the instruction point.

That cycle is compatible with a reuse proof. The proof is the door-open transition on the existing simulation clock. The command generator, the perception focus, and the score sheet stay unread by that transition.

The same chapter lists three later Stage I tests. Each has its own printed procedure and its own score sheet. They stay later.

| Section | Printed start | Physical page checked | Why it waits |

3.4's door is a real alternative if a later review decides that an unnamed command generator makes 3.2 unfit. This reading treats 3.2 as fit because the instruction-point cycle is printed and the missing grammar is an open row, GPSR-OPEN-CMD, rather than a behavior invented from the title.

## Approaches

### Typed task crate on the existing runtime

Add `crates/task_3_2` when implementation is allowed. It depends on `domain` only. It does not depend on `sim_runtime`, `task_3_1`, or the capability crates. `harness` is already the integration crate that may depend on `sim_runtime`. It gains a dependency on `task_3_2` and a private module whose test builds `sim_runtime::Clock`, advances it with `domain::Step`, and passes `clock.now_ms()` to the new machine.

The machine's first events are `DoorOpen`, `Arrived`, and `Tick`. `DoorOpen` from the outside phase emits `GoToPoint`. The announced instruction point stays in the harness scenario. The effect carries no coordinate. `SimWorld::from_seed` stays the section 3.1 layout and is not the GPSR arena.

This is the recommended boundary. It reuses the clock that already exists, leaves the section 3.1 types in place, and gives the next session one executable transition.

### A second fixture copied into the task crate

`task_3_2` would own a clock, a pose, and a door flag, and would never import `sim_runtime`. The transition could still run. The millisecond count and the advance rule would exist twice. That misses the reuse proof this milestone asks for.

### A generic task framework in `domain`

A shared `Task` trait, a phase registry, and a plugin table would try to hold section 3.1 and section 3.2 in one machine. `task_3_1::Trip` would have to move onto that trait, or the trait would sit beside it unused. The first changes the section 3.1 API. The second is a framework with no caller. Neither belongs in this milestone.

## Recommended boundary

`task_3_2` is a typed crate. `harness` is the only new importer of `sim_runtime` for this task, and that import is the clock. `domain` gains no door field, no instruction-point field, and no change to `Observation`, `World`, `Event`, or `EventKind`. `sim_runtime::SimWorld::from_seed` stays the luggage layout.

### Inputs, state, and events

Inputs to the first machine:

- `now_ms: u64`, the count from `domain::Step`. The five-minute limit is printed. Which event arms it, and the inclusive edge, stay GPSR-ASM-CLOCK. The first machine stores the stamp and does not enforce 5 minutes.
- `DoorOpen`, the printed test-start trigger. No door geometry.
- `Arrived`, the adapter's report that the move finished. No coordinate.
- `Tick`, a stamp with no phase change.

State:

- `Outside`, the initial phase.
- `GoingToPoint`, after `DoorOpen`.
- `AtPoint`, after `Arrived` from `GoingToPoint`.

`Arrived` while `Outside` is `OutOfOrder` and leaves the phase unchanged. That is the machine's order for procedure step 2: the move starts when the door is open. A rejection stores nothing.

Events the first machine does not have:

- command text, command success, a return after a command, a timer pause, a score, a penalty, a person id.

### Contracts the first test consumes

- `sim_runtime::Clock::new`, `Clock::advance`, `Clock::now_ms`.
- `domain::Step::from_ms`.
- No `SimWorld`, `SimArm`, `SimBase`, `task_3_1::Trip`, `perception`, `navigation`, `manipulation`, or `hri` call.

## Proof

The scaffold is done, for this milestone's first code review, when both of these are true:

- `task_3_2` builds in the workspace, depends on `domain` only, and a unit test shows `DoorOpen` moving `Outside` to `GoingToPoint` with effect `GoToPoint`.
- A harness test imports `sim_runtime::Clock`, advances it by 25 ms, and the machine's stored stamp is 25 while the phase stays `GoingToPoint`.

That is reuse of the existing clock and one executable transition. It is not a completed GPSR run.

## Non-goals

- Parsing or executing a generated command, including the printed coke example.
- Awarding 3×400, 3×100, 1500, or any penalty.
- Deciding an open row.
- A perception model, a new gripper behavior, a map, or a ROS graph.
- A second world generator, a copied clock, or a task trait in `domain`.
- Hardware, deploy, flash, registration, contact, or spending.
- Editing section 3.1's rules, sheet, or public types.
- Treating this design document as a `pass` row.

## Source ambiguities that stay open

The inventory rows GPSR-OPEN-OUT, GPSR-OPEN-CMD, GPSR-OPEN-RETURN, GPSR-OPEN-HELP, GPSR-OPEN-ABSENT, and GPSR-OPEN-START cannot pass on this text. GPSR-ASM-RETRY, GPSR-ASM-PAUSE, GPSR-ASM-CLOCK, and GPSR-ASM-PLACE may later carry a labeled value. The label stays an assumption.

The live command-generator repository was not read. The PDF names it. A later snapshot of that site is not this rulebook.
